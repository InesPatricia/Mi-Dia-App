# Mutation audit

The phase 5 baseline of the QA arc. It answers a question a green suite cannot answer on its own:
what would these tests catch if the application were wrong.

The method is to break the application on purpose, one defect at a time, and record which level of
the suite goes red. A mutation nothing catches is coverage that looked like it was there and is not.

**This was a snapshot taken for the comparison after phase 6, and that comparison has now been
made.** See **After the refactor**, below. The generated block is the post-refactor run; the
pre-refactor one is the same table, and it is in git history at the commit that closed phase 5.

Measured on commit `247e1a6`, branch `qa/test-architecture`, against the promoted build
`mi-dia-v172` in `public/index.html`. Generated by `node quality/tools/mutate.mjs`. Everything
between the markers is rewritten by that command, and the prose around it is written by hand and
survives a re-run.

## How it was measured

    node quality/tools/mutate.mjs

One Windows machine, 4 cores, headless, Playwright 1.62.1, Node 24. Six mutants across two modules,
three levels each, plus a control run with nothing mutated: the unit level (`node --test` in
`quality/unit`), the integration level (the `integration` Playwright project) and the end-to-end
level (the `mobile-chromium` project, which is the one that gates a merge). Roughly 46 minutes in
total, of which the end-to-end level is 38.

The control run is not a formality. A red level says nothing about a mutant if the suite was already
failing before anything was touched, so the tool refuses to continue unless every level it was asked
to run is green first. It was.

Retries are pinned to 0 for the audit. A retry exists to absorb a transient failure, and here a
failure is the signal being measured. The suite's measured flake rate over 415 executions is 0
(`BASELINE.md`), so nothing is being papered over by turning them off.

Every mutant is applied to two files, because the tree holds two copies of the same code and
different levels read different ones: the module under `src/modules/`, which the unit level loads in
a vm sandbox, and `public/index.html`, which the browser levels serve. That the calc block is
identical in both is not assumed. `mutate.test.mjs` asserts that every anchor occurs exactly once in
every file its mutant names, against the real tree, so a promoted build that reformats the block
turns that test red instead of turning this report quietly wrong.

## How to read a row

**Caught by** names every level that went red. A level that stayed green did not notice the defect.

**SURVIVED** means no level noticed, and it is a question rather than a finding. Either the suite
has a hole there, or the mutation was equivalent: code guarded twice does not change behaviour when
one guard is removed, and that is a fact about the application rather than a gap in the tests. Every
survivor gets a verdict of its own under **Verdicts**, below, written by a person. The tool does not
guess which of the two it is, because it cannot.

## What the numbers say

Four things, none of them visible before the audit ran.

**1. The end-to-end suite catches the ritual arithmetic through two tests.** Three different
arithmetic defects all land on the same pair: "seeded rituals render the Home section with names +
streak" and "tapping the check marks the ritual done, bumps the streak, and persists". Every other
functional test is blind to all three.

That is not an argument for adding tests at that level. It is the measurement behind invariant 5,
that a new case goes to the lowest level that can hold it. The unit level caught all three in about
a second each. The end-to-end level took six minutes to reach the same conclusion through a screen.

**2. The first-run seed can stop working entirely and the gated suite stays green.** This is the
result worth keeping. `seed-writes-nothing` removes the write that gives a new user their two
default rituals, and every execution of the functional level still passed. Only the integration
level, built in phase 4, noticed.

The root cause is in the suite rather than in the application, and the spec that has it says so
itself: `quality/e2e/tests/ritual.spec.js` opens with "the section only renders when rituals exist,
so every test seeds them". Every ritual test writes its own `rituals` key before the page loads, so
none of them ever boots a user who has none, and the seed path is never taken. The onboarding spec
does boot a fresh user, and asserts the onboarding overlay rather than what was seeded behind it.
Nothing in `quality/e2e/tests/` mentions `rit_seeded_v1` at all.

Two consequences. The integration level earned its place by catching something no other level sees,
which is a stronger argument for it than the one phase 4 was built on. And the first run, which is
the only experience every user has exactly once, has no end-to-end coverage. That belongs in the
defect backlog rather than in this file, and it is the kind of case phase 7 exists for.

**3. Both browser levels are blind to the cycle phase arithmetic.** `cycle-phase-off-by-one` moves
the boundary of the menstrual phase by one day, so the last bleeding day reads as follicular. The
unit level catches it. The integration level and the whole functional suite do not.

That is the same shape as the seed result and it points the other way, which is what makes the pair
useful. The seed is written by the application and asserted by no end-to-end test. The cycle phase
is computed by the application and asserted by no end-to-end test either, even though the phase is
visible on screen. Between them they say where the functional suite actually looks, which is at the
ritual cards and very little else of the arithmetic.

**4. One mutant survived every level, and it is the report working rather than the suite failing.**
`streak-guard-bound` was put in the catalogue expecting exactly this. See **Verdicts**.

Six mutations across two modules is a sample rather than a survey, and each one was chosen because
somebody expected it to matter. The honest reading is that the defects most likely to be introduced
in these two modules are each caught somewhere, that where they are caught is uneven, and that the
end-to-end suite contributes less of that catching than its size suggests.

## After the refactor

Phase 6 moved eighteen of the nineteen functional specs onto a page object layer, which is the
change this baseline existed to check. The failure mode of that kind of refactor is silent: an
assertion that quietly stops being made leaves the suite green, the badge unmoved and the count
unchanged, and nothing says so.

The audit was re-run on the migrated suite with the same command, the same six mutants and the same
three levels. **The generated block above is that second run, and it is byte-identical to the
first**, including the names of the tests that failed under each mutant, not only how many.

    diff <(sed -n '/results:start/,/results:end/p' before.md) \
         <(sed -n '/results:start/,/results:end/p' after.md)

That is the claim worth being precise about. It does not say the refactor was correct in general. It
says that for these six defects, the suite's ability to notice them is exactly what it was: the same
levels go red, and the same tests inside those levels go red. A weaker red would have shown up as a
smaller number in a cell, and a swallowed assertion as a green one.

Two things it does not cover. Only six defects were tried, so an assertion lost somewhere none of
them reaches would not appear here. And the two suites are not compared test by test on a green run,
only under mutation, which is the question this file was built to answer rather than the whole of
what a refactor could break.

## Verdicts

Written by hand. The tool reports SURVIVED and stops, because it cannot tell a hole in the suite
from a mutation that changed no observable behaviour.

**`streak-guard-bound`: equivalent. Not a gap.** `streakOf` walks backwards from today and breaks at
the first due day that is not in the log, so the loop's `guard` is a safety bound against a
malformed log rather than a limit any real input approaches. Walking 3999 days instead of 4000
cannot change an answer that is decided within a handful of iterations, and no reachable state of
the application produces a log long enough to tell the two apart. Nothing to fix, and nothing to
cover. A test written to kill this mutant would be a test of the guard rather than of the streak.

This entry is the reason the mutant is in the catalogue. Finding 5 of the arc says an equivalent
mutation is not an uncaught one and needs a verdict of its own, and until this run that column had
never been produced by a real run, only by the harness's own tests. Now the distinction is on the
page, next to a real case, where the next reader meets it before they meet a survivor they have to
judge for themselves.

## Was the mutation actually applied

A mutation that did not apply looks exactly like a mutation nothing caught, so the question has to
be settled before any green cell is read as coverage.

For four of the six, another level going red on the same edit settles it outright. For
`seed-writes-nothing`, where the end-to-end level stayed green, the integration level went red on
the same mutated `public/index.html`, in the same browser engine, inside the same staging of the
mutant. The build the browser was served did carry the defect, and the functional suite ran against
it and did not notice. That is observation rather than inference, and it is why the tool runs every
level inside one staging rather than staging the mutant once per level.

`streak-guard-bound` is the one row where no level went red, so nothing external corroborates it and
the guarantee has to come from the harness. It refuses an anchor that is not unique and one that
does not match, writes each file and then reads it back to confirm the replacement landed at the
offset the anchor occupied, and aborts the whole mutant if any of that fails. The same edit was also
applied and verified through `node quality/tools/mutate.mjs --dry-run` before the run. That is a
weaker kind of evidence than a red test and it is stated as such: the claim is that the file on disk
carried the change, and the verdict above argues separately that carrying it changes nothing anyone
can observe.

The harness restores from its own byte copy through a journal on disk rather than through git. Each
of these guards was broken on purpose and watched to fail before this run was trusted.

## What this does not measure

- **Any module but `ritual` and `cycle`.** `onboard.js` has no mutant at all, and neither does
  anything the two covered modules do outside their calc surface.
- **Most of `cycle`.** One boundary in one function. `nextPeriodStart`, `flowerOpen`, `history` and
  the rest are covered by the unit level and untouched here, so nothing in this report says what the
  browser levels would catch if any of those were wrong. The one measurement taken suggests the
  answer is nothing, which is a reason to widen the sample rather than to assume it.
- **Anything outside the calc layer and the seed.** No mutation touches rendering, i18n, the service
  worker, the theme, or persistence beyond the seed.
- **Whether a mutant was caught for the right reason.** A test that goes red because the screen no
  longer renders counts the same here as one that asserts the number it was written to assert.
- **The quarantine and the production smoke.** The first gates nothing by design, and the second
  needs a live URL.
- **CI.** Every number here was taken on one Windows laptop. The suite runs on Linux in CI, in two
  shards, with two retries, and a mutant caught there in a different place would not be visible from
  here.
